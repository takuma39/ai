# 基本設計とアーキテクチャ設計

> **この記事でわかること**：基本設計が AI の叩き台生成に最も向く理由と、それでも人間が決めなければならないこと。

## 結論

> **基本設計は AI の叩き台生成が最も効果を発揮するフェーズである。ただし「AI が出した設計 = 正解」ではない。**

判断の分かれ目は明確である。

> **AI が提案したパターンの前提条件（想定ユーザー数、チーム規模等）が自プロジェクトに合致するか、必ず検証する。**

AI は一般論として正しい設計を出す。**それがこのチーム・この規模で正しいとは限らない。**

## 背景・課題

アーキテクチャ設計で AI が強いのは、**選択肢を網羅的に並べること**である。人間が3案思いつくところを、AI は10案とその比較表を出す。

一方で AI が判断できないものがある。

| AI が出せるもの | 人間が決めるもの |
| --- | --- |
| 選択肢の一覧 | **どれを採るか** |
| 一般的なトレードオフ | **このチームにとってのトレードオフ** |
| ベストプラクティス | **今の制約下で現実的か** |

### 成果物一覧

`BASIC_DESIGN.md` に**セクション単位で統合する**。外部ツール（Apidog 等）で管理するものはリンクを記載する。

| 成果物 | 内容 | AI 活用ポイント | 扱い |
| --- | --- | --- | --- |
| システム構成図 | 全体アーキテクチャ（C4 モデル等） | Mermaid で構成図を生成 | `## システム構成図` に埋め込み |
| ER 図 | テーブル設計・リレーション | `erDiagram` で叩き台を生成 | `## ER図` に埋め込み |
| API 仕様書 | エンドポイント・リクエスト/レスポンス | Apidog AI で Schema 生成 | `## API仕様` にリンクまたは抜粋 |
| 画面遷移図 | 画面間の遷移とトリガー | `stateDiagram` で生成 | `## 画面遷移図` に埋め込み |
| 非機能要件定義書 | 性能・セキュリティ・可用性 | 要件からの定量化を支援 | `## 非機能要件` に表形式 |

**1ファイルに集約する**ことで、`@docs/basic_design/BASIC_DESIGN.md` の1参照で全体が渡せる。

### アーキテクチャパターンの選定

```text
以下の要件に最適なアーキテクチャパターンを提案してください。

[要件]
- ユーザー数：初期1万人、1年後10万人を想定
- リアルタイム通知が必要
- マイクロサービスとモノリスのどちらが適切か判断したい

[出力形式]
1. 推奨パターンとその理由
2. 代替案との比較表（スケーラビリティ・開発速度・運用コスト）
3. Mermaid記法でのシステム構成図（C4 Container図）
```

**2番目の「代替案との比較表」が要点である。** 推奨だけを出させると、AI の結論をそのまま採用しがちになる。比較表があれば人間が判断できる。

### 構成図の生成

```text
以下のシステム要件から、C4モデルのコンテナ図をMermaid記法で生成してください。

[システム概要]
- フロントエンド：Next.js（Vercel）
- バックエンドAPI：Node.js（Express）
- データベース：PostgreSQL
- 認証：Auth0
- ファイルストレージ：S3

図には各コンポーネント間の通信プロトコル（REST / gRPC / WebSocket等）も記載してください。
```

**通信プロトコルまで書かせる**と、後の実装で迷いが減る。

### ADR で判断を記録する

**なぜその設計にしたか**を残さないと、半年後に同じ検討を繰り返す。

```text
以下のアーキテクチャ判断について、ADR（Architecture Decision Record）を作成してください。

判断内容：認証基盤をAuth0からFirebase Authに移行する
背景：コスト削減と既存GCPインフラとの統合

[ADRテンプレート]
## タイトル
## ステータス（提案 / 承認 / 却下 / 廃止）
## コンテキスト（なぜこの判断が必要か）
## 決定内容
## 結果（トレードオフ・影響範囲）
```

**「却下された選択肢とその理由」が最も価値がある。** これがないと、後から来た人が同じ案を再提案する。

### 過剰設計を検出させる

AI は「足りない」は指摘するが、「多すぎる」は指摘しにくい。**明示的に聞く。**

```text
この設計に含まれる抽象化・拡張ポイントを全て列挙して、
それぞれ「今この段階で必要か」を判定して。

「将来必要になるかもしれない」は必要の理由にしないで。
現時点で使われない抽象化は、削除した場合の構成も示して。
```

### 前提条件を照合する

AI の提案には**暗黙の前提**がある。それを明示させる。

| 確認すること | 例 |
| --- | --- |
| 想定規模 | 「マイクロサービス推奨」は何人規模のチームを前提としているか |
| 運用体制 | 24時間監視できる人員がいる前提になっていないか |
| 予算 | マネージドサービス前提のコストが現実的か |
| 期限 | 初期構築にかかる期間が締切に収まるか |

## 実際のプロンプト例

```text
# 前提条件を明示させる
先ほど提案されたアーキテクチャについて、
その設計が前提としている条件を全て列挙して。

- 想定するチーム規模と体制
- 想定するトラフィック規模
- 想定する運用体制（監視・オンコール）
- 前提としている予算感

それぞれ、私のプロジェクトの実情（[実情を記載]）と照合して、
合わない前提があれば指摘して。
```

```text
# 却下理由まで記録させる
この設計判断を ADR として記録して。

特に「検討したが却下した選択肢」と「却下の理由」を厚く書いて。
半年後に別の人が同じ案を再提案しないための記録として書いて。
```

```text
# 設計レビュー（3観点）
この基本設計を次の観点でレビューして。

1. スケーラビリティのボトルネック
2. セキュリティ上の懸念
3. 過剰設計（今は要らない抽象化）

3つ目を特に厳しく見て。
「将来必要になるかもしれない」は残す理由にしないで。
```

## 注意点

> **「AI が出した設計 = 正解」ではない。** 最終判断は必ず人間が行う。AI の提案は選択肢の一覧であって、決定ではない。

> **前提条件を必ず検証する。** 「マイクロサービス推奨」という提案が、100人規模のチームを前提としていることがある。自分の実情と照合する。

> **ADR に却下理由を残す。** 決定内容だけでは、後から同じ検討を繰り返す。

> **過剰設計は明示的に聞かないと出てこない。** AI は「足りない」を指摘するが「多すぎる」は指摘しにくい。

> **`BASIC_DESIGN.md` に集約する。** 図やファイルが散らばると、実装時に `@` 参照が煩雑になる。
