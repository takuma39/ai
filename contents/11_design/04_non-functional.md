# 非機能要件設計

> **この記事でわかること**：「速くしてほしい」を数値目標に変換させる方法と、AI が出した数値をそのまま使ってはいけない理由。

## 結論

非機能要件の要点は1つである。

> **「速くしてほしい」「落ちないようにしてほしい」のような曖昧な表現を排除し、必ず数値目標を設定する。**

そして AI の使い方には制約がある。

> **AI が出力した目標値は、業界標準やプロジェクトの予算・体制と照合して調整する。**

AI は一般的な数値を出す。**その数値を満たすためのコストと体制が自分たちにあるか**は、AI には判断できない。

## 背景・課題

非機能要件は「後回しにされ、いつの間にか決まっていない」項目の代表である。

理由は明確で、**数値を決めるには根拠が要る**からである。「p95 300ms」と書くには、それが必要な理由と、達成可能な根拠が必要になる。

だから曖昧なまま残る。そして AI に実装させると、**AI は非機能要件を考慮しない実装を返す**。

```mermaid
flowchart LR
    A["非機能要件が未定義"] --> B["AI は「動くもの」を作る"]
    B --> C["本番で性能問題が発覚"]
    C --> D["設計からやり直し"]

    style A fill:#ffedd5,stroke:#ea580c,color:#000
    style C fill:#fee2e2,stroke:#dc2626,color:#000
    style D fill:#fee2e2,stroke:#dc2626,color:#000
```

## 具体的な方法

### 定量化させる

```text
以下のシステムについて、非機能要件を具体的な数値目標とともに定義してください。

[システム概要]
- BtoB SaaS（プロジェクト管理ツール）
- 想定ユーザー数：初期500社 / 1年後2,000社
- 同時接続：ピーク時500ユーザー

[定義してほしい項目]
1. パフォーマンス（レスポンスタイム、スループット）
2. 可用性（SLA、RPO/RTO）
3. スケーラビリティ（負荷増加への対応方針）
4. セキュリティ（認証方式、暗号化、監査ログ）
5. 運用性（バックアップ、モニタリング、アラート基準）

[出力形式]
| カテゴリ | 要件 | 目標値 | 計測方法 |
```

**「計測方法」の列が要点である。** 測れない目標は達成判定ができない。「p95 レイテンシ 500ms 以下（Datadog の APM で計測）」まで書く。

### AI の数値をそのまま使わない

AI が出す数値は「一般的にこのくらい」である。3点で照合する。

| 照合先 | 確認すること |
| --- | --- |
| **業界標準** | 同種のサービスで妥当な水準か |
| **予算** | その水準を満たすインフラ費用が出せるか |
| **体制** | SLA 99.99% は 24時間対応の体制を前提としていないか |

**「SLA 99.99%」は月間ダウンタイム約4分である。** これを本気で目指すなら、オンコール体制と冗長化構成が要る。数値だけ書いて体制がないと、達成できない目標が残る。

### 5カテゴリの押さえどころ

| カテゴリ | 決めるべき最小限 |
| --- | --- |
| **パフォーマンス** | p95 レイテンシ / スループット / 同時接続数 |
| **可用性** | SLA / RPO（どこまでデータ損失を許容するか）/ RTO（どれだけで復旧するか） |
| **スケーラビリティ** | 負荷増加時の対応方針（垂直 / 水平 / 自動） |
| **セキュリティ** | 認証方式 / 暗号化（保存時・転送時）/ 監査ログの保持期間 |
| **運用性** | バックアップ頻度と保持 / 監視項目 / アラート閾値 |

**RPO / RTO が最も抜ける。** 「バックアップは取っています」だけでは、障害時に「どこまで戻せるか」が分からない。

### 実装に渡す

非機能要件は書いて終わりではない。**実装時に AI へ渡す。**

```text
@docs/basic_design/BASIC_DESIGN.md の「非機能要件」セクションを踏まえて実装して。

特に次を満たすこと：
- p95 レイテンシ 500ms 以下（N+1 クエリを作らない）
- 監査ログに操作者・対象・日時を記録する
- 個人情報をログに出力しない
```

**渡さないと考慮されない。** 「一般的に良い実装」と「この非機能要件を満たす実装」は別である。

### 検証可能にする

数値目標は**検証手段とセットにする**。検証できれば AI が自己修正できる（→ [`../00_overview/00_what-is-ai-driven-dev.md`](../00_overview/00_what-is-ai-driven-dev.md)）。

| 目標 | 検証手段 |
| --- | --- |
| p95 レイテンシ | 負荷試験 / APM での計測 |
| N+1 の不在 | クエリログの確認 / ORM のログ出力 |
| 監査ログの記録 | テストでログ出力を検証 |
| 個人情報の非出力 | ログ内容の検査テスト |

### 段階的に決める

すべてを最初に決めなくてよい。**リリース前に必要なものから順に決める。**

```mermaid
flowchart LR
    A["① セキュリティ<br/>（認証・暗号化・ログ）"] --> B["② 可用性<br/>（RPO/RTO・バックアップ）"]
    B --> C["③ パフォーマンス<br/>（実測してから調整）"]
    C --> D["④ スケーラビリティ<br/>（負荷が見えてから）"]

    style A fill:#fee2e2,stroke:#dc2626,color:#000
    style B fill:#ffedd5,stroke:#ea580c,color:#000
    style C fill:#dbeafe,stroke:#2563eb,color:#000
    style D fill:#f5f5f5,stroke:#6c757d,color:#000
```

**セキュリティは後から足せない。** 一方でパフォーマンス目標は、実測してから調整するほうが現実的である。

## 実際のプロンプト例

```text
# 曖昧な要件を数値化させる
@docs/spec/SPEC.md から、数値化されていない非機能要件を全て抜き出して。

各項目について：
- なぜ数値化が必要か
- 数値を決めるために私に確認すべきこと
- 参考になる一般的な水準（ただし推奨はしない）

を提示して。数値を勝手に決めないで。
```

```text
# 目標値の実現可能性を検証させる
以下の非機能要件を満たすために必要な体制・インフラ構成・
概算コストを整理して。

[非機能要件]
- SLA 99.99%
- RTO 15分
- p95 レイテンシ 300ms

現在の体制（[体制を記載]）で達成可能か判定して。
達成できない場合、どの水準なら現実的かを提示して。
```

```text
# 実装が非機能要件を満たしているか検証
@docs/basic_design/BASIC_DESIGN.md の非機能要件と、
@src/api/orders/ の実装を突き合わせて。

満たしていない可能性がある箇所を、根拠とともに列挙して。
特に N+1 クエリ・ログへの個人情報混入・監査ログの欠落を重点的に。
```

## 注意点

> **AI が出した数値をそのまま採用しない。** 業界標準・予算・体制と照合する。「SLA 99.99%」は月間4分のダウンタイムであり、相応の体制が要る。

> **「計測方法」を必ず書く。** 測れない目標は達成判定ができず、いずれ形骸化する。

> **RPO / RTO を決める。** 「バックアップは取っている」だけでは、障害時にどこまで戻せるか分からない。

> **実装時に渡さないと考慮されない。** 非機能要件は書いて終わりではない。プロンプトに含める。

> **セキュリティを後回しにしない。** 後から足せない項目である。パフォーマンスは実測後に調整できる。
