# プロンプトチートシート

> **この記事でわかること**：各フェーズで最も使用頻度が高いプロンプトの型。コピーして使う前提の一覧。

## 結論

フェーズごとに**1つだけ覚える**なら、次の6つである。

| フェーズ | 型 |
| --- | --- |
| 要件定義 | 「**質問して**から SPEC.md を書いて」 |
| 設計 | 「スケーラビリティ・セキュリティ・**過剰設計**の観点でレビューして」 |
| 実装 | 「`@既存ファイル` のパターンに従って。実装後に**テストを実行**して」 |
| テスト | 「**先に失敗するテスト**を書いてから実装して」 |
| レビュー | 「`@SPEC.md` に照らして。セキュリティ・性能・仕様準拠を確認して」 |
| リファクタ | 「**挙動を保つこと**。前後でテストを実行して」 |

いずれも**検証手段が組み込まれている**のが共通点である。

## 背景・課題

毎回ゼロからプロンプトを考えるのは非効率で、しかも品質がばらつく。**型を持てば、誰が書いても一定の水準になる。**

ただし型は出発点であって完成品ではない。プロジェクト固有の情報（ファイルパス・規約）を足して使う。

## 具体的な方法

### フェーズ別チートシート

| フェーズ | プロンプト | 詳細 |
| --- | --- | --- |
| **要件定義** | `Interview me about [feature]. Ask about edge cases, constraints, and tradeoffs. Write SPEC.md.` | [`../10_requirements/`](../10_requirements/) |
| **設計** | `Review this architecture for scalability bottlenecks, security, and over-engineering risks.` | [`../11_design/`](../11_design/) |
| **実装** | `Implement [feature] in @[file]. Follow patterns in @[example]. Run tests after implementing.` | [`../13_implementation/`](../13_implementation/) |
| **テスト** | `Write failing tests for [feature], then implement to make them pass.` | [`../15_test/`](../15_test/) |
| **レビュー** | `Review this PR against @SPEC.md. Check for security, performance, and spec compliance.` | [`../14_code-review/`](../14_code-review/) |
| **リファクタ** | `Refactor @[file] to improve [concern]. Preserve all behavior - run tests before and after.` | [`../13_implementation/`](../13_implementation/) |

> **プロンプトの言語について**：上記は英語だが、**日本語でも大きな差は出にくい**。チーム標準の言語を統一しておくと、ナレッジ共有がスムーズになる。

### 日本語版

そのまま使える形にしたものである。

```text
# 要件定義
[機能名] について私にインタビューして。
エッジケース・制約・トレードオフを質問して。
私が答えていない項目は推測せず、必ず聞いて。
全部揃ったら docs/spec/SPEC.md を作成して。
```

```text
# 設計レビュー
このアーキテクチャを次の観点でレビューして。

1. スケーラビリティのボトルネック
2. セキュリティ上の懸念
3. 過剰設計（今は要らない抽象化）

3つ目を特に厳しく見て。将来必要になるかもしれない、は理由にしないで。
```

```text
# 実装
@[対象ファイル] に [機能] を実装して。
@[参考ファイル] のパターンに従って。
実装後に npm test を実行して、失敗したら根本原因を直して。
テストを緩めて通すことはしないで。
```

```text
# テスト（TDD）
[機能] に対して、まず失敗するテストを書いて。
テストが失敗することを確認してから実装に進んで。
実装は、テストが通る最小限に留めて。
```

```text
# レビュー
この PR を @docs/spec/SPEC.md に照らしてレビューして。

観点：セキュリティ / 性能 / 仕様準拠
指摘は [Blocker] / [Suggestion] / [Nit] で分類して。
```

```text
# リファクタリング
@[ファイル] を [観点] の改善のためリファクタして。

制約：
- 挙動を一切変えないこと
- リファクタ前にテストを実行し、後にも実行して、結果が同じことを確認して
- 挙動を変える必要があると判断したら、実施せずに報告して
```

### 状況別の追加パターン

```text
# 調査（メインを汚さない）
サブエージェントを使って [対象] を調査して。
メインの会話には「該当ファイル一覧」と「要約3行」だけ返して。
```

```text
# 原因究明（対症療法を防ぐ）
[エラー全文] で失敗する。
根本原因を特定して修正して。エラーを握りつぶさず、
try-catch で隠すような対処もしないで。
```

```text
# 影響範囲の確認
[関数名] のシグネチャを変更したい。
呼び出し元を全て列挙して、それぞれ必要な修正を表にして。
まだ変更はしないで。
```

```text
# 判断を仰がせる
[タスク] を実装して。
仕様に書かれていない判断が必要になったら、
推測で進めずに実装を止めて質問して。
```

### チートシートを自分のものにする

型をそのまま使うのではなく、**プロジェクト固有の情報を埋め込んだ版**を作る。

```mermaid
flowchart LR
    A["汎用の型"] --> B["プロジェクト固有の<br/>パス・規約を埋める"]
    B --> C[".claude/commands/ に<br/>コマンド化"]
    C --> D["チームで共有"]

    style A fill:#f5f5f5,stroke:#6c757d,color:#000
    style B fill:#dbeafe,stroke:#2563eb,color:#000
    style C fill:#ede9fe,stroke:#7c3aed,color:#000
    style D fill:#dcfce7,stroke:#16a34a,color:#000
```

効果が高かったプロンプトはコマンド化する（→ [`02_versioning.md`](02_versioning.md)）。

## 実際のプロンプト例

```text
# チートシートをプロジェクト仕様に落とす
このリポジトリの構成・規約を読んで、
汎用のプロンプトチートシートをこのプロジェクト向けに書き換えて。

実際のパス（テストコマンド、仕様書の場所、参考にすべき既存実装）を
埋め込んだ形にして。
```

```text
# よく使うプロンプトをコマンド化する
私が過去によく使っていた指示のパターンを踏まえて、
.claude/commands/ に登録すべきコマンドを3つ提案して。

それぞれ、どういう場面で使うか（description）も書いて。
```

## 注意点

> **型は出発点である。** プロジェクト固有の情報（ファイルパス・テストコマンド・規約）を足さないと効果が半減する。

> **全部の型を覚えようとしない。** 実際に使うのは2〜3個である。使ったものだけコマンド化する。

> **英語と日本語を混在させない。** チームで言語を統一しておくと、プロンプトの共有・改善がしやすい。

> **「テストを緩めて通すな」は毎回書く。** AI は失敗したテストを通すために、アサーションを弱める近道を取ることがある。
