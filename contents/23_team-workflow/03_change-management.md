# チェンジマネジメントとモチベーション

> **この記事でわかること**：ツール導入より難しい「意識改革」と、モチベーションが激減する典型パターン。

## 結論

AI 駆動開発への移行では、**ツール導入と同等以上に重要なものがある**。

> **エンジニアの意識改革とモチベーション管理。**

そして最も避けるべき事態が明確にある。

> **「AI が作った負債の手直しばかりさせられている」という不満。** これが生まれるとモチベーションが激減する。

対策は、AI を**「ただの自動生成機」ではなく「優秀なペアプロ相手」**として扱う文化の醸成である。

## 背景・課題

AI 導入に反対するエンジニアは、多くの場合「新しい技術が嫌い」なのではない。

**自分の仕事が「AI の後始末」に変わることを警戒している。**

```mermaid
flowchart LR
    A["AI が大量にコードを生成"] --> B["ブラックボックス化"]
    B --> C["人間は手直しだけ"]
    C --> D["「これは自分の仕事か？」"]
    D --> E["モチベーション激減"]

    style A fill:#dbeafe,stroke:#2563eb,color:#000
    style C fill:#ffedd5,stroke:#ea580c,color:#000
    style E fill:#fee2e2,stroke:#dc2626,color:#000
```

**この懸念は正しい。** 実際にそうなっているチームがある。だから「気にしすぎ」と扱わない。

## 具体的な方法

### 価値観の移行（パラダイムシフト）

移行が必要なのは、**喜びの源泉**である。

| これまで | これから |
| --- | --- |
| 自分の手で1からコードを書く喜び | **システム全体を上位レイヤーで設計し、AI のアウトプットをレビュー・構築してスピーディに価値を届ける喜び（アーキテクトとしての喜び）** |

**「コードを書かなくなる」ではなく「別の喜びに移る」**という説明が要る。前者だけを伝えると、単に仕事を奪われる話に聞こえる。

### AI-TDD の負債化を防ぐ

不満が生まれる構造は明確である。

| 状態 | 結果 |
| --- | --- |
| AI 任せでブラックボックス化 | 「AI が作った負債の手直しばかり」→ **モチベーション激減** |
| **人間主導のコードレビューと設計判断の機会を確保** | AI は「優秀なペアプロ相手」→ 主導権が人間に残る |

**「人間が設計判断をする機会を必ず残す」**のが対策である。全部を AI に投げない。

### 役割の変化を言語化する

漠然と「役割が変わる」と言われても不安になる。**具体的に示す。**

| 従来の開発者の役割 | AI 駆動開発での役割 |
| --- | --- |
| コードを **書く** | **仕様を書き**、AI にコードを生成させる |
| コードを **レビューする** | AI の出力を **レビュー・修正する** |
| テストを **書く** | AI が生成したテストを **検証・補強する** |
| バグを **修正する** | AI のデバッグを **監督・判断する** |

> **開発者の役割は「コードを書く人」から「AI の出力をキュレーションし、品質を担保するアーキテクト」へシフトする。**

**「なくなる」ではなく「移る」**であることが表で見える。

### 反対の理由を聞く

「使ってくれない」と嘆く前に、**なぜ使わないかを聞く**。理由によって対処が違う。

| 理由 | 対処 |
| --- | --- |
| **手直しが増えると感じている** | 適用範囲を絞る。設計判断の機会を残す |
| 品質が信用できない | レビュー体制を示す。品質メトリクスを見せる |
| **使い方が分からない** | オンボーディングの問題。ペアプロで見せる |
| **速くなった実感がない** | 測る。ベースラインと比較する |
| セキュリティが不安 | 権限設計・ゲートウェイの構成を説明する |

**「速くなった実感がない」には測定で答える。** 感覚の議論を続けても平行線になる（→ [`04_quality-metrics.md`](04_quality-metrics.md)）。

### 「レビュー時間が減らない」への答え

よくある指摘である。**これは正しい観察であることが多い。**

```mermaid
flowchart LR
    A["実装時間：短縮"] --> C["合計：変わらない？"]
    B["レビュー時間：増加"] --> C
    C --> D["👤 測って判断する"]

    style A fill:#dcfce7,stroke:#16a34a,color:#000
    style B fill:#ffedd5,stroke:#ea580c,color:#000
    style D fill:#dbeafe,stroke:#2563eb,color:#000
```

対処は2つある。

- **PR を小さくする**（1セッション1課題を守る）
- **人間が見る観点を絞る**（機械的な指摘は AI と linter に任せる）

「レビューが増えた」は、**PR が大きすぎるサイン**であることが多い（→ [`../14_code-review/00_ai-human-split.md`](../14_code-review/00_ai-human-split.md)）。

### 巻き込む範囲を広げる

プロンプトライブラリの改善に、**エンジニア以外も参加させる**。

| 役割 | 貢献 |
| --- | --- |
| PM | 仕様作成プロンプト、受け入れ基準の書き方 |
| ドメインエキスパート | 業務ルールの正確な表現 |
| デザイナー | デザインレビューの観点、ペルソナ定義 |

**自分が作ったものは使われる。** 参加が定着の最短経路になる。

### 成功体験を早く作る

抽象的な説得より、**1つの成功体験**が効く。

| 選ぶタスク | 条件 |
| --- | --- |
| 退屈で機械的 | AI が明らかに得意 |
| 影響範囲が小さい | 失敗しても被害が小さい |
| **本人が面倒だと思っている** | 効果を実感しやすい |

**「本人が面倒だと思っているタスク」から始める。** 押し付けられたタスクでは、効果を感じても素直に評価されない。

## 実際のプロンプト例

```text
# 反対理由を整理する（人間同士の対話の準備）
チームメンバーから AI 導入について次の懸念が出ている。

[懸念の内容]

この懸念が「正しい観察」なのか「誤解」なのかを判定して。
正しい観察の場合、どう対処すべきか具体案を出して。
「気にしすぎ」という結論は出さないで。
```

```text
# 成功体験になりそうなタスクを探す
このリポジトリの Issue とコミット履歴を読んで、
「退屈で機械的、影響範囲が小さく、担当者が面倒だと思っていそう」な
タスクを3つ挙げて。

AI で試すのに適している理由も添えて。
失敗した場合の影響も評価して。
```

```text
# レビュー時間の実態を測る
過去2ヶ月の PR を gh で取得して、次を比較して。

- AI 導入前後での PR あたりの変更行数
- レビューコメント数
- 作成からマージまでの時間

「レビュー時間が増えた」という感覚が事実か検証して。
事実なら、PR の大きさが原因かも分析して。
```

## 注意点

> **反対理由を「気にしすぎ」で片付けない。** 「AI の後始末ばかりになる」という懸念は、実際にそうなっているチームがある以上、正当である。

> **人間が設計判断をする機会を必ず残す。** 全部を AI に投げると、確実にモチベーションが下がる。

> **「コードを書かなくなる」と伝えない。** 「別の喜びに移る」という説明が要る。前者だけでは仕事を奪われる話に聞こえる。

> **「速くなった実感がない」には測定で答える。** 感覚の議論は平行線になる。ベースラインと比較する。

> **成功体験は本人が面倒だと思っているタスクから作る。** 押し付けられたタスクでは素直に評価されない。

> **エンジニア以外も巻き込む。** 自分が作ったものは使われる。参加が定着の最短経路である。
